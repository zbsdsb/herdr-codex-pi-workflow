# Run Manifest And Round Isolation

## Configuration Resolution

Load model and lifecycle defaults in this order:

1. User config: `~/.herdr-codex-pi-workflow/config.json`.
2. Optional project override: `<repo>/.herdr/codex-pi-workflow.json`.
3. Explicit user request for this run.

The project file may override only the relevant fields under `roles` and `workflow`. It must not contain credentials. Before starting, write the resolved configuration snapshot into `state.json` and `RUN.md` so later configuration edits do not silently alter an active run.

The task root is always `~/.herdr-codex-pi-workflow/tasks/<repo>/<run-id>`. Worktrees live under `~/.herdr-codex-pi-workflow/worktrees/<repo>/<run-id>/<repository-name>`. New runs use state schema 4 and the normalized `repositories[]` contract in `state-and-gates.md`; legacy singular `repo/worktree/reviewed_commit` fields are read-only compatibility inputs.

Resolve `active_profile` and merge its role overrides before applying project and run-specific overrides. Then apply an explicit per-round `model_override` / `thinking_override` only when the Coordinator's task request contains one. Store the fully resolved configuration snapshot, each override's source and reason, in the run state. The effective process launch arguments must match this snapshot.

## Durable Run Directory

```text
~/.herdr-codex-pi-workflow/tasks/<repo>/<run-id>/
├── README.md                    # 总览与导航唯一入口（gen-nav 生成；先看这里）
├── RUN.md                       # 人类可读总控账本（顶部含状态行）
├── state.json                   # 唯一机器真相源（schema v4）
├── events.jsonl                 # append-only 状态迁移历史
├── PREFLIGHT.md
├── REQUIREMENTS.md
├── FINDINGS.json
├── FINDING-TRACEABILITY.md
├── PLAN.md
├── PLAN-SUMMARY.md              # 手机可审摘浆（gen-plan-summary 生成）
├── RISK-ASSESSMENT.json         # freeze 生成的风险触发项和最低模式证据
├── PLAN-REVISION-01.md
├── SOL-ADVISORY.md
├── ESCALATION.md
├── rounds/
│   ├── 01/
│   │   ├── REMEDIATION.md
│   │   ├── IMPLEMENTATION.md    # 含 finding disposition table
│   │   ├── TEST-RESULTS.md
│   │   └── REVIEW.md
│   └── 02/
├── DELIVERY-MANIFEST.json       # 显式交付目录/接口场景契约
├── DEPLOYMENT.md
├── VERIFICATION.md              # release 模式
├── FINAL-AUDIT.md               # release 模式
├── decision.json                # 用户决策记录（append-only，channel/state revision 标记）
├── .workflow.lock/              # run 级互斥锁（短生命周期）
└── .pending-mutation.json       # 崩溃恢复用待提交 mutation（正常情况下不存在）
```

`state.json` is the machine truth; `events.jsonl` is its append-only transition history. `README.md` is the canonical human entry point and is generated by `gen-nav`; `RUN.md`, `tasks/index.json`, and goal state are projections. `docs/开发功能/<功能名>/README.md` is the separate business handoff projection. Lifecycle changes use `herdr-workflow.mjs transition`; round creation uses `round`; plan hashes and mode/config freeze use `freeze`; decisions use `record-decision`. Mutations take `.workflow.lock`, increment `state_revision`, and use `.pending-mutation.json` for crash recovery. `reconcile --write` may repair projections but never alters lifecycle state or evidence, and only records a successful reconciliation after its audit passes.

`FINDINGS.json` and `FINDING-TRACEABILITY.md` are updated after every Review and before every remediation round. Every round records the effective model/thinking source, attempt/session identity, prompt hash, checkpoint, Git heads, exact tests, and failure classification. At each transition the script refreshes navigation and index atomically; goal state is then updated as an observation mirror.

## RUN.md Required Sections

```markdown
# <run title>

## Objective
## Acceptance Criteria
## Scope And Non-Goals
## Requirement Decisions
## Resolved Configuration
## Repository And Worktree
## Preflight
## Planner
## Sol Advisory
## Rounds
## Deployment Approval
## Final Outcome
```

Each entry in **Rounds** must list:

- round number and timestamp;
- implementation branch and exact base/current commit;
- agent kind, configured model/thinking, Herdr pane ID, native agent session ID/path;
- artifact paths;
- exact test commands and high-level result;
- reviewer verdict and blocking finding count;
- decision to continue, validate, pause, or deploy.

Never record secrets, `.env` values, token text, cookies, or raw customer data.

## Codex Hook Isolation And MCP Startup Observation

When Planner or Reviewer runs from a repository containing a project `.codex/hooks.json`, create a run-owned empty `codex_cwd` outside the Trellis project root and pass it through Codex `--cd`. Add the real repository, implementation worktree, and run directory explicitly with `--add-dir`; do not copy project hooks into `codex_cwd`. This mutes only the project Trellis `UserPromptSubmit` hook for that Codex process while preserving user-level Herdr lifecycle hooks. Do not default to `features.hooks=false`, because that can disable Herdr state reporting. Record `codex_cwd`, `hook_isolation`, and every added directory in `state.json` and `RUN.md`.

Before sending any Planner or Reviewer task, snapshot `codex mcp list`, start the no-task session, and enforce the configured `codex_mcp_startup_grace_ms` no-input window. The default grace period is 60 seconds. During that window no prompt, Enter, model switch, focus/resize, or other terminal input is allowed. After the grace period, record the model title, input prompt, enabled servers, `ready/failed/unknown` statuses, warnings, and elapsed time from the same session when available. MCP readiness is advisory when `codex_mcp_require_all_enabled=false`: a failed, interrupted, or unknown server sets the startup observation to `DEGRADED` but does not block the single Planner/Reviewer task injection. Do not send a probe or restart repeatedly just to complete the MCP list. If task injection itself fails, record a workflow/environment incident and require an explicit retry decision. Persist the observation and any degraded risk in `state.json` and `RUN.md`.


## Build And Release Authority

`local-no-service` compilation is diagnostic evidence only. Debug/test builds in an isolated test environment are acceptance evidence only. The authoritative Release build is the project's CI system after explicit user approval of the exact reviewed commit and release operations. Before that approval, no push/tag/Release/image publication is allowed. Record CI run IDs/URLs, commit, artifacts, release verification, and rollback target in `DEPLOYMENT.md`.

Every Reviewer writes per-repository `reviewed_commits` into that round's `metadata.json`; the strict Review gate compares this map with `repositories[].reviewed_commit`. Prose in `REVIEW.md` is explanatory evidence, not the machine commit binding.

Every round records a test environment classification:

```text
local-no-service
remote: <approved-test-environment>
```

Only static analysis, pure unit tests, and service-free compilation may run on the development machine. Tests requiring a running backend, Docker/Compose, Postgres, Redis, real HTTP, browser E2E, or multiple services run in an approved isolated environment through the project's remote-operations wrapper. Do not invoke raw `ssh`, `scp`, or `rsync`. Remote test commands, exit codes, logs/artifact paths, and any cleanup are recorded in `TEST-RESULTS.md`.


Before Planner starts, the Coordinator must use the installed `grill-me` Skill when any condition applies:

- authorization, permissions, identity, data exposure, payment, deletion, migration, production deployment, or external side effect;
- changes span multiple service boundaries, APIs, persistence, scheduling, or frontend behavior;
- the user request leaves semantics, scope, conflict behavior, or acceptance criteria unresolved;
- the Coordinator cannot state a testable requirement contract in `REQUIREMENTS.md`.

Load and follow `grill-me` directly. Ask one question at a time, include a recommended answer, and inspect the codebase instead of asking questions whose answer is available locally. Persist each resolved decision in `REQUIREMENTS.md` and `RUN.md`.

For explicit, low-risk, locally bounded fixes, record why the gate was skipped in `RUN.md`.

## Pane And Session Lifecycle

### Preflight

- Runs once per run, before `REQUIREMENTS.md` is finalized, when the request involves non-trivial repository facts.
- Create a **new** pane in the current tab rooted at the main repository; start a **new** native Pi session with the configured Preflight model and thinking.
- The Preflight agent is read-only: only `read`, `grep`, `find`, and `ls`; it must not edit source, tests, Git state, or workflow files other than `PREFLIGHT.md`.
- Send it the unchanged original user request, the repository root, repository rules, and the `PREFLIGHT.md` path.
- Validate the verdict (`PREFLIGHT_READY`), record its session/pane metadata in `state.json` and `RUN.md`, then close the pane.
- A failed or timed-out preflight is recorded as `preflight_failed`; the Coordinator continues from the original request and writes `REQUIREMENTS.md` directly. The brief is advisory only and never overrides the user request.
- Preflight is skipped for extension commands, slash commands, steering messages, empty input, and image-bearing requests, consistent with the trigger rules.

### Planner

- Start once, using the configured native Codex model.
- Write `PLAN.md`, calculate and record the requirements/plan hashes, verify the verdict (`PLAN_READY`).
- **Planner pane stays in standby during `AWAITING_PLAN_APPROVAL`**: if the user requests tweaks during plan review, the active session modifies `PLAN.md` incrementally using warm memory without cold re-exploration.
- **Close Planner pane only after user plan approval**: freeze plan hash, record session metadata, close the pane, then transition to `IMPLEMENTING`.
- Planner does not participate in implementation or review rounds.
- If requirements or architecture materially change during later implementation rounds, start a new `plan-revision-N` Codex pane and write `PLAN-REVISION-N.md`.

### Each Implementation Round

1. Create a **new** Implementer pane in the current tab, rooted in the same implementation worktree.
2. Start a **new** Pi session with configured Implementer model and thinking.
- Give it `REQUIREMENTS.md`, active plan/revision, `FINDINGS.json`, `FINDING-TRACEABILITY.md`, `rounds/NN/REMEDIATION.md`, prior review when present, current diff, repository rules, and this round's artifact paths.
4. After `rounds/NN/IMPLEMENTATION.md` and `rounds/NN/TEST-RESULTS.md` are validated, record its session/pane metadata in `state.json` and `RUN.md`.
5. Send no further work to that Implementer. Close only the pane created by this workflow after artifacts are verified.

### Each Review Round

1. Create a **new** Reviewer pane in the current tab, rooted in the implementation worktree.
2. Start a **new** native Codex session with configured Reviewer model.
3. Give it requirements, active plan/revision, `FINDINGS.json`, `FINDING-TRACEABILITY.md`, `rounds/NN/REMEDIATION.md`, current diff, implementation/test artifacts, and this round's `rounds/NN/REVIEW.md` path.
4. Validate the verdict and record metadata.
5. Close the Reviewer pane after artifact verification, regardless of PASS or CHANGES_REQUESTED.

A CHANGES_REQUESTED verdict starts the next numbered implementation round with a new Pi session. A PASS never starts deployment automatically.

### Sol Consultation

- Created only when the Coordinator explicitly calls a Sol consultation for one concrete high-risk decision (architecture, security, persistent-host, public-contract, failed-verification, or user-requested), typically before an `ARCHITECTURE_GATE` or the hard-stop escalation.
- Create a **new** pane in the current tab and start a **new** native Pi session with the configured Sol model and thinking.
- The Sol agent receives no mutating tools: read-only at most, and it must not modify the worktree, implement, or decide.
- Send it one precise question, the risk class, and compact evidence (not raw secrets, full sessions, or vendor configs).
- Write its recommendation to `SOL-ADVISORY.md`, validate the verdict (`SOL_ADVISORY`), record metadata, and close the pane.
- The advisory is input to the user's gate decision; it is never an authorization to deploy or proceed.

## Pane Closure Preconditions

Before closing any per-round pane:

- required artifact exists, is non-empty, and has a valid final verdict;
- agent session/pane identity is recorded in state and RUN.md;
- current Git HEAD and `git status --short` are recorded;
- no agent is `working` or `blocked`;
- close only the exact pane created by the workflow.

If a pane cannot be closed, retain it, mark `closure_pending` in state, and continue only after no further prompt will be sent to it.
